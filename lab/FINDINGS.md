## 1. Migration Job restarts indefinitely / invalid Job spec

**Symptom:** Source handout `lab/broken-chart/templates/migrate-job.yaml` contained `restartPolicy: Always`, which Kubernetes does not permit for a Job pod template. A Job requires `Never` or `OnFailure`.

**Actual post-fix evidence from recorded run:**

```text
job.batch/migrate condition met
job.batch/migrate   Complete   1/1           7s
  PASS  migrate Job completed
```

**Cause:** The Job's pod restart policy used the Deployment-style value `Always`.

**Fix:** Changed `restartPolicy` to `Never` in the migration Job's Helm template. The Job controller handles retry logic using `backoffLimit`.

**How I found it:** Inspected the chart's `kind: Job` and pod spec before installing. Followed up with `kubectl -n debug-lab wait --for=condition=complete job/migrate` and `./scenario.sh verify`. I did not capture the original failed Job admission in a cluster, so the above is confirmation of the repaired state, not a claimed reproduction of the original failure.

## 2. Metrics CPU violates namespace LimitRange

**Symptom:** The supplied `values.yaml` requested `cpu: "2"` and limited `cpu: "4"` for `metrics`, while the supplied immutable `cluster-state/limits.yaml` sets a per-container maximum of `cpu: "1"`. Such a pod is rejected by admission when LimitRange is active.

**Actual post-fix output:**

```text
limitrange/debug-lab-guardrails created
    metrics:
     Limits:
       cpu:     200m
     Requests:
       cpu:      50m
```

**Cause:** Both original CPU values exceeded the namespace's one-core container maximum.

**Fix:** Set `metrics.resources.requests.cpu: 50m` and `limits.cpu: 200m`. No environment files were changed.

**How I found it:** Compared the original chart values against the supplied `LimitRange` and checked the real Deployment resource values using `kubectl -n debug-lab describe deploy metrics`. The quoted output confirms the corrected resource values; a failing admission attempt using the original CPU values was not recorded.

## 3. Gateway references the wrong backend namespace

**Symptom:** The supplied gateway environment variable was `BACKEND_URL: "http://backend.default.svc:8080"`; the backend Service is actually installed into `debug-lab`.

**Actual live Service and Deployment output:**

```text
service/backend    ClusterIP   10.96.31.100    <none>        8080/TCP   3m3s   app=backend
      BACKEND_URL:  http://backend.debug-lab.svc.cluster.local:8080
```

**Cause:** The gateway URL targeted namespace `default` rather than `debug-lab`.

**Fix:** Changed the URL to `http://backend.debug-lab.svc.cluster.local:8080`.

**How I found it:** Compared the URL in the chart to `scenario.sh`'s target namespace and `kubectl get svc`, then inspected the live Deployment env with `kubectl describe deploy gateway`. HTTP behaviour could not pass while port defect #5 remained; correcting the DNS name alone was not sufficient.

## 4. Reporter RBAC is bound to the wrong ServiceAccount

**Symptom:** The reporter Deployment used `serviceAccountName: reporter` but the original RoleBinding's subject was `name: default`.

**Actual output from the live verifier:**

```text
  PASS  ServiceAccount debug-lab/reporter can list pods
```

**Cause:** A RoleBinding grants access to its configured subject, not automatically to the account with the same name as the Role.

**Fix:** Updated `lab/broken-chart/templates/rbac.yaml` to bind the namespace-scoped Role to the `reporter` ServiceAccount; retained pod-only `get` and `list` verbs.

**How I found it:** Traced `.spec.template.spec.serviceAccountName` to RoleBinding `subjects[].name`. The recorded validation used `kubectl auth can-i list pods -n debug-lab --as=system:serviceaccount:debug-lab:reporter` and `./scenario.sh verify`.

## 5. Readiness and Service port do not match the prebuilt app

**Symptom — real Kubernetes event:**

```text
Warning   Unhealthy   pod/backend-...   Readiness probe failed:
Get "http://10.244.0.17:8080/healthz": dial tcp 10.244.0.17:8080: connect: connection refused
```

**Actual container log:**

```text
2026/11/21 03:33:19 eb-debug-app 2.0.0 starting: mode=api pod=backend-bf84ddf78-8c474 listening on :8081 (image default is 8081; set PORT to override)
```

**Cause:** The supplied container defaults to port `8081`, but the Helm chart probes and Services use `8080`. This affected backend, gateway, reporter, metrics and worker readiness.

**Fix:** Added `PORT: "8080"` to the application environment for all five deployments. Kept the Service ports and `/healthz` probes as specified, rather than changing the app's public Service contract.

**How I found it:** After resolving the startup compatibility issue, `kubectl get pods` showed `0/1` readiness; Kubernetes events showed `connection refused` at `8080`; `kubectl logs deploy/backend` explicitly revealed that the binary listens on `8081` unless `PORT` is set.

## 6. Worker cache cannot be created on a read-only root filesystem

**Symptom — actual worker log:**

```text
2026/11/21 03:36:10 FATAL: worker could not initialise its cache: mkdir /var/cache/app: read-only file system — the process needs a writable directory at /var/cache/app (mount a volume there, or set CACHE_DIR)
```

The worker entered `CrashLoopBackOff` and the verifier reported one crash-looping pod.

**Cause:** The worker needs to write to `/var/cache/app`; the supplied chart deliberately enforces `readOnlyRootFilesystem: true` without any writable volume at that path.

**Fix:** Mounted an `emptyDir` volume at `/var/cache/app` only in the worker Deployment, preserving the otherwise read-only root filesystem. The cache is ephemeral, appropriate for this temporary worker state.

**How I found it:** `kubectl -n debug-lab get pods -o wide` reported `CrashLoopBackOff`; `kubectl -n debug-lab logs deploy/worker --previous` gave the exact path and operation that failed. The manifest change addresses that path without removing the workload or changing the provided image.

## Additional runtime compatibility issue observed during testing

The **first cloud run** exposed a seventh, environment-specific obstacle before the application could start. Kubernetes events for all six containers reported:

```text
Error: container has runAsNonRoot and image has non-numeric user (nonroot), cannot verify user is non-root
```

The prebuilt image declares a **named** user, but our runner's kubelet/container runtime could not verify its numeric UID in combination with `runAsNonRoot: true`. To preserve non-root enforcement, I added `runAsUser: 65532` alongside `runAsNonRoot: true` to the supplied-image workload templates. This was needed to get the lab running on this kind runner; it is recorded separately from the six chart defects above. Neither the image nor the cluster guardrails was changed.

- **The full verifier is not yet green.** The latest recorded run shows 7/11 PASS (migration, backend/gateway/worker/metrics readiness, no crash loops and reporter RBAC). Four failures remain (reporter readiness and three short-lived probe results). Manual BusyBox probes independently received HTTP 200 from backend and gateway and DNS resolved `backend.debug-lab.svc.cluster.local`; however, the verifier’s `kubectl run --rm -i --quiet` captured only late output (`PROBE_REPORTER_BODY=`, `PROBE_DNS=fail`), missing early backend/gateway lines. This is evidence of a probe attach/output race on this runner, not evidence those Services are broken. The reporter application log showed `pod list failed: parse pod list: unexpected end of JSON input`; a separate Pod with the same ServiceAccount observed a TLS handshake failure contacting `https://kubernetes.default.svc`. I would next isolate the API server/service TLS issue and rerun the unchanged verifier on a fresh kind environment. I did **not** edit `scenario.sh` or `cluster-state/`, fabricate a green run, or change the provided image.
